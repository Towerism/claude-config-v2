# Memory-store triage

A memory's body loads only when its one-line index description gets it recalled, so a rule that must fire every time, or that a machine could enforce, is weak as a memory. This skill finds each memory a stronger home, or confirms it stays. It proposes; nothing moves until the user approves.

**Scope**, unless the user names other stores:
- the global store, `${XDG_DATA_HOME:-~/.local/share}/claude-memory/*.md`
- the current project's store, `~/.claude/projects/<project>/memory/`
- the CLAUDE.md files that load in this session (global and repo)
- the skill folders: `~/.claude/skills/`, the global store's `skills/`, and skills in plugins installed from the user's own marketplaces (`~/.claude/plugins/`). Only some of these can receive a moved rule (step 3.3); the rest count only as coverage (step 3.2).

## Steps

1. **Inventory.** List every memory in scope with its description, and read every body (descriptions are too short to judge). With more than about 40 bodies, split the reading across parallel `explore` or `scientist` agents, each returning one row per memory: name, store, kind (rule, fact, or ticket state), bytes, one-line rule, the situations it applies to. Brief them with the destination rules of step 3 (especially 3.3's real-file test), so they don't propose invalid homes. Also record the always-loaded cost for the report: the bytes of every CLAUDE.md in scope plus each project `MEMORY.md`, since the index loads every session too. Run the check script of memory-graph-check (step 8) once and note the global memories its "left out of the session index" finding lists; steps 2, 6 and 8 use that list. Done when every memory has a row and the baseline bytes and left-out list are noted.
2. **Find duplicates across stores.** For each project memory, check whether a global memory states the same rule. Mark a full restatement `delete`. When the project copy adds project facts (names, paths, tickets), mark it `trim to the project facts`. A global memory on step 1's left-out list does not count as a duplicate, because it never loads. Done when every project memory is marked duplicate, partial or unique.
3. **Pick each memory's home.** Take the first destination that fits, and write the reason in one clause:
   1. **Machine enforcement**: a permission deny in `settings.json`, a Claude Code hook, a git hook or a lint rule can make the mistake impossible (for example, a tool that must never be called). The memory stays only to explain the reason. Why: enforcement never depends on recall.
   2. **Already stated elsewhere**: grep the CLAUDE.md files and the skill that owns the procedure for the rule's key phrase. If one already states it, mark the memory `delete`, or `covered by <file>` when the rule also applies outside that skill. Coverage needs reach as well as text: open the covering file (a name or heading match is not enough, and a cited `references/` file must exist), and a global memory is covered only by text that ships to every machine (the synced config repo, a plugin skill, or the global store's `skills/`; not a skill in this machine's `~/.claude/skills` alone) and loads in every situation the rule applies to (a learned skill loads only when the prompt contains one of its triggers). Why: in one triage all 11 "covered by a skill" calls failed these checks.
   3. **Belongs in a skill**: the rule only matters while one procedure runs (reviewing a PR, writing a ticket, an eval loop). Offer only a skill whose `~/.claude/skills/<name>/SKILL.md` is a real file: `p=~/.claude/skills/<name>; [ ! -L "$p" ] && [ ! -L "$p/SKILL.md" ] && [ -f "$p/SKILL.md" ]`. A skill that lives only in `~/.omc/skills`, the global store's `skills/`, a repo's `.omc/skills` or a plugin, or is linked into `~/.claude/skills`, is not a destination. Why: a skill outside `~/.claude/skills`, or only linked there, may stop loading or get deleted, and the rule goes with it (global memory skill-homes-only-in-claude-skills). Name the skill file and the step it joins, and the skill's source of truth (synced config repo, a shared repo its SKILL.md names, or an unversioned local copy). A global memory may move only into a skill whose source of truth is the synced config repo, since step 3.2's reach test rejects the others. Before moving anything, send each pair to an independent `critic` agent with only the memory and skill files, and move only what it rates `SAFE`: every sentence fits the skill, the skill does not contradict or forbid it, and the skill loads wherever the rule applies. A rule that fires on Claude's own planning, with no user prompt naming the skill, fails that last test. For `PARTLY SAFE`, copy only the named sentences and keep the memory. Back up an unversioned skill before editing it. Why: the user called moves into skills lossy, and in one triage 19 of 20 proposed moves failed (rules fired outside the skill's triggers, skills were stale or forbade the action, and quotes and precedents had no home in the skill).
   4. **CLAUDE.md**: it must shape most tasks before anything would recall it (evidence standards, safety around deletes or secrets). Name the file (global or repo). When the target text sits between deploy markers (such as `<!-- CLAUDE-CONFIG:START -->`), name the source file the deployer reads instead (grep the user's config repos for the marker name to find the deployer), because a sync overwrites edits to the deployed copy. Keep this list short, because every CLAUDE.md line costs context in every session. Rules that fail silently or unsafely in most repos of a workspace qualify (a credential-leaking flag, a command that hangs, a cache that must be committed), and so do short rules that are exceptions to a global rule or apply across topics, since no topic file would load for all their cases (for example "send release-PR review requests instead of drafting them"). Run a cheap spike on every command a promoted line prescribes: in one triage a "prefix every read-only git command" line broke `git show` on unfetched history and needed a fallback.
   5. **Triggered reference file**: situational memories that share a moment of use (deploying, red CI, Jira CLI writes, Slack drafts, a release) are grouped into one reference file, and one row in a CLAUDE.md "Reference files" table names that moment and the file's path. The members then leave the index. Put the files where the user chooses; the default is next to the CLAUDE.md that triggers them, under a shared prefix such as `claude-<topic>.md`. Write each trigger row to cover every situation its members applied to, including symptoms (a failing deploy job, a command that silently does nothing) and cases that a person or a repo name triggers. Why: the user wants situational memories grouped "into a reference file, [so] that reference file can be triggered from CLAUDE.md at the right moment" (global memory group-situational-memories-into-triggered-references).
   6. **Team**: teammates should get it through a shared plugin or repo.
   7. **Stays a memory**: all others, typically live ticket state and one-off facts with no group.

   Done when every memory has a destination and a reason.
4. **Check recall for memories that stay.** Each description must name the situations that should recall it, not only the incident that taught it. The global store's index cuts descriptions at 110 characters. Mark descriptions to rewrite. Done when every staying memory is marked `ok` or has a proposed description.
5. **Report and ask.** Show a table grouped by destination: memory, destination with the file and step, reason. For CLAUDE.md lines, give the estimated bytes they add to every session; for reference files, the members and the trigger row. Then the duplicates to delete, then the description rewrites. List any memory that contradicts a CLAUDE.md rule as a question for the user, never resolved in either direction on your own. Ask which groups to apply. Done when the user has picked.
   Then write the approved mapping to a scratch file: every memory under exactly one destination, with what each trim or merge drops and why. Check with a script that every memory name appears in it, and brief every later executor and verifier from that file. Done when the coverage check passes.
6. **Back up, build the survivors, and verify before deleting.** The survivor is the file whose text replaces what is removed: the global duplicate from step 2, the covering file from step 3.2, or a reference file or promoted CLAUDE.md line from steps 3.4-3.5. Nothing is deleted in this step.
   1. Back up. A project store: `tar czf ~/.claude/projects/<project>/memory-backup-<YYYYMMDD>.tgz -C <store> .` (outside the store, so the sync and the index ignore it). The global store needs none, because its git history keeps deleted files. Copy a CLAUDE.md that is not under git, and each unversioned skill you will edit, to a dated backup next to the project store.
   2. Build the survivors from the mapping. Reference files: an executor keeps every claim, each memory's Why, dated incidents and user quotes, and rewrites `[[links]]` to members as "see <file>, <section>". CLAUDE.md lines: you write them. Trims: made in place. Before trimming ticket-state memories, read each ticket's current status in the tracker yourself and pass it in. Brief the trim executor to keep user quotes that condition an approval, still-true decisions and facts that constrain future work, and to list every fact it drops. Why: in one triage a trim dropped an approval's conditions and a spike result the plan depended on.
   3. Have a `critic` agent compare each promoted CLAUDE.md line with its memory (weakened or strengthened hedges, dropped triggers, fallbacks or exceptions, conflicts with the rest of the file, restated rules), and apply its fixes now, while the memory still exists.
   4. Send the picked deletions and trims, with the backup copies as the originals, in batches of about 10-15, to independent `verifier` agents in parallel, with the user's reason for caution if they gave one. Ask each to try to refute its batch:
      - list every claim in the memory (rule, exception, threshold, nuance-carrying example, user quote, project fact future work depends on) and find each in the survivor;
      - check the survivor's reach as in step 3.2. For a reference file, check that its trigger row fires in every situation the original applied to, and propose exact row wording for each gap, or, when no row wording covers it, the CLAUDE.md line instead (step 3.4). A global memory counts as reach only if it is not on step 1's left-out list; content dropped in favour of a left-out global memory goes back into the survivor;
      - for a ticket-state note, use the status you passed in, and find a home for every unfiled follow-up, open loose end and user rule it holds;
      - return `SAFE`, `MERGE-FIRST` with the exact sentences and target file, or `KEEP` with the reason.

   A project-only fact goes to a project memory, never into the global store. Done when every picked deletion and trim has a verdict; `KEEP` overrides the pick (restore a trimmed memory from its 6.1 backup), and you tell the user which ones.
7. **Apply the picks.**
   - Apply `MERGE-FIRST` sentences and trigger-row fixes before deleting the memory they came from.
   - Keep the reason and the incident behind each CLAUDE.md promotion: in its memory, or in a "Background for CLAUDE.md rules" section of the matching reference file when the memory is grouped (then the memory can go once step 6 rated it `SAFE`).
   - Rewrite inbound `[[links]]` to deleted memories; step 8 lists any that remain. Run shell loops over a list of names under `bash`, because zsh does not split `$VAR` into words.
   - Global store edits: Write or Edit only. To delete a global memory, `rm` the file, then Read any store file so the sync hook carries the deletion.
   - Enforcement: load the `update-config` skill for permissions and Claude Code hooks; add git hooks or lint rules in the repo they guard.
   - Team: hand the list to `share-philosophy-not-preference` as its own task. Keep each personal memory until the shared version ships, then delete it unless it holds something personal the shared version left out.
   - Project stores: update `MEMORY.md` for every file removed or changed. Refresh the hooks of trimmed memories, and when memories moved to reference files, add one line saying where situational material now lives. Report the always-loaded bytes (CLAUDE.md plus `MEMORY.md`) before and after.

   Done when every picked change is made, every reference file has its CLAUDE.md trigger row, every touched `MEMORY.md` lists only files that exist, and the team list (if any) has been handed off.
8. **Check the graph.** Read `${XDG_DATA_HOME:-~/.local/share}/claude-memory/skills/memory-graph-check.md` and follow it over every touched store, passing the deleted names. A same-name pair it reports goes back to the user as a step-2 duplicate, or is listed as one they declined to merge. Global memories you saved during the triage take index budget and can push others out, so compare the left-out list with step 1's and tell the user which memories newly dropped out. Done when the check reports nothing beyond findings listed for the user.
